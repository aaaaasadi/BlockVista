Bitmap (Bit Vector) Structure

1 bit per block: 1 = Allocated | 0 = Free
RAM: 8 Bytes
How OS Allocates: Scans bits linearly (often word-at-a-time via CPU instructions) for the first 0 bit and flips it to 1.
How OS Frees: Calculates bit position: WordIndex = Block / 32 and flips bit to 0 in O(1).

Free Block Linked List Structure

Pointers embedded directly within unallocated disk blocks
Free Nodes: 0
How OS Allocates: Pops the block at HEAD: HEAD = HEAD->next. Zero RAM overhead outside the disk.
How OS Frees: Prepends freed block to HEAD: FreedBlock->next = HEAD; HEAD = FreedBlock in O(1).

Operating Systems Theory & Viva Reference

Core concepts, memory analysis, and comparative trade-offs
METHOD 1

Bit Map (Bit Vector)

A Bitmap is an array of bits where each bit corresponds directly to one disk block on the storage volume:

  • 0 represents a FREE block ready for allocation.
  • 1 represents an ALLOCATED block in use by a file or directory.
  • Scanning: The OS scans words sequentially to find 0 bits. Hardware instructions (e.g., bitwise NOT and find-first-set) make finding the first free block extremely fast.
  • Contiguous Allocation: It is trivial for the OS to locate $k$ contiguous free blocks by checking if $k$ consecutive bits are 0.
  • Storage Overhead: Requires $\frac{D}{8}$ bytes of RAM/disk, where $D$ is total disk blocks. For a 1 TB disk with 4 KB blocks (256 million blocks), the bitmap takes only 32 MB.
METHOD 2

Linked List of Free Blocks

A Free Block Linked List links all unused disk blocks together into a chain:

  • Pointers in Free Blocks: The OS stores the disk address of the next free block inside the free block itself! Because the block is empty, this consumes 0 bytes of extra memory.
  • Superblock Pointer: The OS keeps only a single HEAD pointer in the disk superblock / main memory.
  • Allocation: Takes $O(1)$ to pop the block at HEAD: new_head = HEAD->next.
  • Deallocation: Takes $O(1)$ to push a freed block to HEAD: freed_block->next = HEAD; HEAD = freed_block.
  • Drawback: Finding contiguous blocks is inefficient because traversing the linked list requires reading disk blocks into memory (heavy disk I/O).

Q1: Why does a 0 represent a Free block and 1 represent an Allocated block in our Bitmap? +

Standard OS conventions (such as UNIX and Linux ext2/3/4) use 0 for free and 1 for allocated so that a bitwise AND or checking against 0xFF can quickly detect fully allocated bytes without testing bit-by-bit. (Some older texts use 1 for free, 0 for allocated, but the 1=Allocated / 0=Free is the standard industry implementation).

Q2: Where is the Linked List pointer stored? Does it waste disk space? +

No extra space is wasted! When a disk block is free, user data is not stored in it. Therefore, the OS writes the 4-byte or 8-byte disk address of the next free block inside the first bytes of the free block itself. Only the HEAD pointer needs to be maintained in the superblock in RAM.

Q3: Why is Bitmap preferred over Linked List in modern operating systems? +

Modern OS filesystems (ext4, NTFS, APFS) prioritize contiguous allocation to minimize disk seek times and file fragmentation. Bitmaps allow the OS kernel to scan RAM for contiguous runs of zeros in microseconds. A linked list would require reading blocks from physical disk, incurring milliseconds of I/O latency.

Q4: How much RAM is needed for a Bitmap on a 512 GB disk with 4 KB block size? +

Formula: $\text{Total Blocks} = \frac{512 \times 10^9}{4 \times 10^3} = 128{,}000{,}000 \text{ blocks}$.
$\text{Bitmap size in bytes} = \frac{128{,}000{,}000}{8} = 16{,}000{,}000 \text{ bytes} \approx 16 \text{ MB}$.
For a modern computer with 16 GB RAM, 16 MB is a negligible 0.1% memory overhead.
